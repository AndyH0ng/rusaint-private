# 증명서 발급 연동 조사

조사일: 2026-11-15. Chrome MCP로 숭실대학교 KICA증명 사이트의 실제 사용자 세션에서 확인했다.
후속 조사에서 국문 재학증명서 1통을 선택하여 PDF 결제 전 단계까지 진행했고, 별도로 일반 인터넷발급의
국문 장학금지급증명서 1통을 0원으로 신청 완료했다. 유료 결제·외부 전송·실물 출력은 실행하지 않았다.
인증 토큰, 쿠키, 학적 개인정보는 이 문서에 기록하지 않는다.

## 결론

rusaint-mcp에 로그인, 학적 조회, 증명서 종류와 옵션 조회, 보관함 조회를 구현할 수 있는 웹 경로를 확인했다.
Rust HTTP 클라이언트로의 재현은 아직 검증하지 않았다. macOS에서 원본을 열거나 출력하는 기능은 미확인이다.
무료 장학금 증명서의 서버 발급까지 확인했으나, 현재 조사만으로 “맥에서 원본 파일 수신·출력 가능”으로 안내해서는 안 된다.

## 확인한 인증 경로

로그인 화면의 `doportallogin` 핸들러는 다음 SmartID 주소로 이동한다.

```text
https://smartid.ssu.ac.kr/Symtra_sso/smln.asp?apiReturnUrl=https://certi.ssu.ac.kr/servlet/WMLOGIN
```

기존 브라우저 SSO 세션으로 인증이 완료되었다. 콜백은 `/servlet/WMLOGIN`에 `sToken`, `sIdno`를 전달하고,
브라우저에서 `COMMAND=SSOLOGINNEW` 단계로 진행했다. 콜백 중간 폼과 쿠키 설정 전체는 아직 분석하지 않았다.
URL에 인증 토큰이 포함되므로 전체 URL을 로그에 남기지 않아야 한다.

프로젝트의 `packages/rusaint-sso/src/lib.rs`에 공유 `SsoCredentials`가 있으므로 새 서비스도 이를 사용할 수 있다.
기존 u-saint의 SAP 세션과 KICA 사이트의 세션은 별도로 취급해야 한다.

## 조회 흐름

사이트의 `Service()` 함수와 실제 화면 이동에서 다음 흐름을 확인했다.

| 단계 | 경로/명령 | 확인 결과 |
| --- | --- | --- |
| 전자증명서 안내 | `/servlet/WMETC?COMMAND=INFO`, `SERVICE_TYPE=FILE` | PDF증명서 신청 메뉴 존재 |
| 학적 선택 | `/servlet/WMMEMBER?COMMAND=GIWANLIST` | 로그인 사용자 학적 조회 성공 |
| 증명서 준비 | `/servlet/WMCERT?COMMAND=CERTWAITING` | 학적 선택 후 대기 화면 |
| 증명서 목록 | `/servlet/WMCERT?COMMAND=CERTILIST` | 발급 가능한 종류 및 선택 옵션 조회 성공 |
| 보관함 | `/servlet/WMBASKET?COMMAND=BASKETLIST` | 조회 성공, 현재 신청 내역 없음 |

전자증명서 경로에서 `FILETYPE=P`, 기관 코드 `GIWANNO=021163`을 확인했다.
폼에는 그 외 서비스 상태 필드도 있으므로 위 값만으로 요청이 충분하다고 가정하지 않는다.

학적 화면의 `ok_submit()`은 서버가 제공한 `Inner_*` 필드를 선택된 학적에 맞춰 상위 폼 필드에 복사한다.
`HAKBUN`, `HAKWI`, `HAKWI2`, `HAKWA`, `HAKWA2`, `KNAME`, `ENAME`, `SANGTAE`, `SANGTAENO`,
`JOBSUBGPCD`, `KORENG`이 포함된다. 영문명이 없으면 영문 증명서 신청을 제한한다.

확인한 국문 종류는 교육비납입증명서, 등록금납부확인서, 봉사활동증명서, 성적증명서, 수료증명서,
장학금지급증명서, 재적증명서, 재학증명서, 학적부사본, 학적부성적이다.
목록은 사용자 학적에 따라 달라질 수 있다. 연도·학기, 성적 표기 방식, 주민번호 노출 등 선택 옵션이 존재한다.
종류와 코드를 고정하지 말고 실제 응답을 파싱해야 한다.

## 로컬 프로그램 의존성

공개 스크립트 `/wm1.0/jscript/reportx.js?ver=1`에서 확인했다.

```text
POST /servlet/WMBASKET, COMMAND=PREVIEWENC
  → 응답 d.res
  → iframe src = http://127.0.0.1:65432/SSO?PARAM=dzreportx: + d.res
```

일부 브라우저 분기는 `https://127.0.0.1:65433`을 사용한다.
테스트 출력은 `COMMAND=TESTPREVIEW` 응답을 같은 방식으로 넘긴다.
따라서 웹 출력 경로는 브라우저의 기본 인쇄 기능만으로 끝나지 않는다.
`d.res`의 내부 형식과 암호화 여부는 분석하지 않았다.

다운로드 링크는 `ICT_REPORTX_SETUP.exe`와 `ICT_DOCULINKREADER_SETUP.exe`를 제공한다.
전자증명서 안내의 `pdfReq()`에는 Mac에서 신청·결제만 가능하고 열람은 Windows에서 가능하다는 안내가 명시되어 있다.

## 파일 다운로드 경로와 미확인 사항

보관함 스크립트에는 다음 명령이 있다.

- `certPDFdownok()` / `certMINdownok()`: `INDEX`, `SGTS`를 설정하고 `COMMAND=CERTPDFDOWN`으로 폼 제출.
- `certSELdownok()`: `FTYPE=B`에서 `CERTPDFDOWN`, 그 외 `CERTMINDOWN`을 선택하는 코드가 있으나,
  해당 함수의 실제 submit 호출은 주석 처리되어 있다.
- `SGTS`: 브라우저 로컬 시각을 `yyyyMMddHHmmss`로 구성한다.

이는 HTTP 기반 파일 수신 후보를 보여주지만, 실제 파일 다운로드에는 성공한 것이 아니다.
보관함 안내에는 `.html` 사용법과 `.min` 증명서를 함께 제출하라는 문구도 있다.
PDF 메뉴, MIN 안내, 전용 뷰어 안내가 혼재하므로 명령 이름만으로 일반 PDF라고 판단할 수 없다.
정상 발급 파일의 Content-Type, 파일 헤더, 암호화/플러그인 요구 여부를 확인해야 한다.
다운로드 가능 기간은 결제일부터 30일로 안내되어 있다.

## 구현 순서

1. 별도 KICA HTTP 클라이언트에서 공유 SSO 토큰으로 인증 콜백·중간 폼·쿠키 처리를 재현한다.
2. 학적·증명서 목록·옵션·보관함을 읽기 전용 API로 구현하고 실제 브라우저 조회 결과와 비교한다.
3. 이미 정상 발급된 파일로 다운로드 및 macOS 열람을 검증한다. 현재 보관함에는 검증할 파일이 없다.
4. 결과에 따라 원본 파일 다운로드를 MCP에 제공하거나 Windows 프로그램 필요 상태를 명시한다.
5. 신청·결제 기능은 금액과 선택 옵션을 사용자에게 제시할 수 있게 설계한다.

교내 발급기 소프트웨어나 통신은 이번에 조사하지 않았다. 발급기가 별도 API를 쓰는지,
장치 인증 또는 전용망을 요구하는지는 확인되지 않았다.

## 후속 조사: 무료 증명서와 PDF 수수료 구분

사용자는 과거 Safari에서 장학금 내역을 무료로 출력했다고 설명했다.
조사자가 선택한 국문 재학증명서 PDF 경로에서는 다음 흐름과 금액을 확인했다.

```text
CERTILIST → POSTBASKET → POSTGAJUBSU
파일형식: PDF증명서
결제금액: 3,000원
```

결제는 실행하지 않았다. 이 금액을 장학금 증명서나 모든 발급 방식에 일반화해서는 안 된다.
일반 인터넷발급 수수료 안내(`WMETC?COMMAND=INFO`, `SERVICE_TYPE=INTERNET`, `SUBNUM=3`)에는
`장학금 지급 확인서 (무료발급)`가 명시되어 있다. 교육비납입증명서도 u-SAINT 경로는 무료라고 별도로 안내한다.
이는 무료 발급 종류/경로가 존재한다는 근거지만 장학금 PDF 다운로드의 최종 금액이 0원임을 검증한 것은 아니다.

일반 인터넷발급 경로로 전환하여 학적을 선택한 뒤 `CERTWAITING`으로 진행했다.
이후 브라우저 MCP 읽기 요청이 일시적으로 응답하지 않았으나, 다음 조사에서 탭이 `CERTILIST`에 도착한 것을 확인했다.
Safari MCP에서 열린 탭은 발견되지 않아 과거 이용 경로는 확인하지 못했다.

### 무료 발급 실증 및 원본 출력 경계

국문 장학금지급증명서 1통, 기간 2024년 1학기~2026년 2학기로 다음 흐름을 실행했다.

```text
CERTILIST → POSTBASKET → POSTGAJUBSU → POSTBASKETLIST
  총 가격: 0원, 처리 결과: 완료
→ WMPAY?COMMAND=NEWPAYMENTFREE
  보관함: 장학금지급증명서, 신청/출력: 1 / 0
```

이 흐름에서 실행한 함수는 `form_submit()`, `ok_submit()`, `gointernetfree()`다.
일반 출력 발급은 서버에서 정상 완료되었고 실제 출력은 하지 않았다. 보관함 안내상 출력 기한은 신청일부터 30일이다.
이메일 원본 전송 버튼은 별도로 1건당 1,000원이라고 표시되므로 무료 출력과 구분한다.

발급된 문서의 `EXECHECK` 응답을 조회했다. 해당 페이지는 로컬 `/SSO_ETC`에 XHR을 보내 설치 여부를 확인하며,
실패하면 `ICT_REPORTX_SETUP.exe`로 이동한다. 성공 시 부모 창의 `preview1()`을 호출한다.
Safari/default 분기도 HTTPS의 `127.0.0.1:65433/SSO_ETC`를 사용하며, 별도 웹 PDF 분기는 보이지 않는다.

발급된 문서에 대해 실제 `PREVIEWENC` 요청을 실행한 결과:

- HTTP 200, `application/json;charset=utf-8`, 키는 `res`.
- `res`는 920자 Base64 문자열이며 디코딩하면 688바이트의 불투명한 바이너리다.
- PDF 헤더나 읽을 수 있는 문서 URL은 없다. 암호화 여부와 내부 구조는 미확인이다.
- 결과는 로컬 프로그램에 전달할 입력이며, 이 응답을 원본 PDF 파일로 취급할 수 없다.

공개 설치 파일을 실행하지 않고 확인했으며 PE32 Windows 실행 파일, Inno Setup 5.5.7 형식이다.
내부 프로그램의 문서 수신·복호화·렌더링 동작은 아직 분석하지 않았다.

현재 구현 가능성이 실증된 범위는 SSO 브라우저 인증, 학적/종류 조회, 무료 발급 신청, 보관함, 네이티브 호출용 응답 수신이다.
Rust HTTP 재현 및 네이티브 출력 대체 구현은 별도 작업으로 남는다.

## EXE 분석 후속 결과: 원격 Linux MCP를 목표로 한 문서 수신

목표 실행 환경은 사용자 Mac이 아니라 gcloud의 Linux MCP 서버다. 아래 실증은 로컬 분석 환경에서 수행했고,
gcloud 서버 실행이나 운영 MCP 배포는 아직 하지 않았다.

설치 파일 SHA-256:
`88f5b0ad4edb5265615d2cde0dcd6bfa4b4dfd1804da592cbd395fa672e988b8`.
`innoextract`로 설치 파일을 풀었고 Windows 설치 프로그램이나 서비스는 실행하지 않았다.
`REPORTX.exe`, `REPORTXSvc.exe`, OpenSSL DLL, 인쇄 보호 DLL 등이 포함되어 있다.
본체에는 Delphi 및 FastReport VCL 구성요소가 있다.

### 실증한 처리

1. REPORTX 실행 인자 해석 함수와 문서 요청 코드를 정적으로 분석했다.
2. REPORTX의 순수 암호 연산 함수 두 개만 Unicorn x86 에뮬레이터에서 호출했다.
   Windows API, 프로그램 진입점, 서비스, 인쇄 코드는 호출하지 않는다.
3. 본인 발급 문서의 `PREVIEWENC` 응답을 해석했다. 내부에는 `URLCheck`, `URLFile`, `URLPost`,
   `TPID`, 문서 번호, 출력 매수 등 실행 인자가 들어 있다.
4. 실행 인자에서 얻은 문서 수신 경로에 HTTPS GET을 보냈다.
   경로는 `/wm1.0/jsp/report/sendfile.jsp`, 파라미터는 `TPID`, `MIN_NO`, `GIWAN_NO`다.
5. 실제 발급된 무료 장학금 증명서의 2,000,000바이트 응답을 받았다.
6. 문서 번호를 사용하는 암호 처리와 압축 해제를 재현하여 2,375,781바이트 문서 데이터를 얻었다.
   앞부분의 1,476,841바이트는 FastReport `preparedreport` XML이며, 준비된 페이지 2개를 확인했다.
   별도 이미지 데이터도 포함된다.

ARIA 계열의 192비트 구성과 MD5 기반 키 변환을 확인했다. 일반 OpenSSL ARIA 명령으로 해석한 결과는
일치하지 않아, 현재 실험 도구는 분석한 버전의 연산 코드를 에뮬레이션한다.
암호 방식 이름만으로 표준 ARIA와 완전히 호환된다고 가정하지 않는다.

### 재현 도구

`tools/certificate_probe.py`는 Python, pefile, Unicorn으로 작성한 실험 도구다.
분석한 버전의 REPORTX 본체와 본인 세션에서 받은 Base64 응답을 입력으로 받는다.
실행 인자 상수는 제공한 실행 파일에서 읽고 문서 접근 토큰은 로그에 출력하지 않는다.
출력 디렉터리 0700, 파일 0600으로 문서·실행 인자를 보관한다.

```sh
uv run tools/certificate_probe.py \
  --exe /private/path/REPORTX.exe \
  --preview /private/path/preview.b64 \
  --output-dir /private/path/certificate-output
```

동일 발급 문서에 대해 위 도구로 다운로드·복호화·압축 해제 재실행에 성공했다.
받은 개인정보 문서는 저장소에 넣지 않고 임시 경로에만 저장했다.
Python 구문 검사와 `git diff --check`를 통과했다. Rust 코드는 수정하지 않았다.

### 남은 작업과 현재 결론

- EXE 없이 서버에서 발급 문서 데이터를 수신하는 데 성공했으므로, 원격 MCP 구현의 가능성은 확인됐다.
- gcloud Linux에서 pefile/Unicorn 실행을 검증하고, 브라우저 인증·신청 단계를 Rust HTTP 클라이언트로 옮겨야 한다.
- FastReport 데이터는 PDF가 아니다. 서버에서 페이지·글꼴·이미지·직인·문서 검증 표시를 재현할 렌더러가 필요하다.
- 단순히 내용을 새 PDF에 옮긴 결과를 공식 원본 PDF라고 취급해서는 안 된다. 원본성과 제출 가능성은 별도 검증 대상이다.
- 현재 도구는 PDF를 생성하거나 출력 완료 콜백(`printcomplete.jsp`)을 전송하지 않는다.
- 운영 rusaint-mcp 도구 추가·배포는 아직 하지 않았다.

## 유료 결제 연결 실증 (gcloud Linux)

국문 재학증명서 PDF 1통, 3,000원 신청 건으로 결제창 연결을 시험했다.
제출처는 숭실대학교, 용도는 일반용으로 설정했다. 카드 입력·사용자 인증·승인/매입은 하지 않았다.

### 직접 결제 URL 전달의 한계

학교 결제 페이지는 `WMPAY?COMMAND=GETMID`에서 주문번호·금액·결제수단에 맞는
`LGD_HASHDATA`, `LGD_MID`, `LGD_TIMESTAMP`를 받은 후 Toss XPay로 폼을 제출한다.
기존 안내에는 U+가 남아 있지만 실제 스크립트와 결제창은 Toss Payments였다.

학교 로그인 쿠키가 없는 별도 브라우저 컨텍스트에서 PG 결제 URL을 열어 카드 선택 화면과
3,000원 금액을 확인했다. 다만 취소 후 학교 `returnurl.jsp`가
`parent.payment_return(...)`을 호출하다 `parent.payment_return is not a function` 오류를 냈다.
PG URL만 넘겨서는 결과 처리가 완성되지 않는다.

### gcloud 콜백 중계 실증

기존 gcloud VM의 Linux x86_64, Python 3.11 환경에서 운영 MCP와 분리한 임시 서버를 실행했다.
별도의 10분 제한 Cloudflare quick tunnel을 사용했으며 운영 서비스·포트·설정은 변경하지 않았다.

학교가 생성한 결제 폼을 그대로 사용하되 다음을 변경했다.

- `LGD_RETURNURL`: 임시 gcloud 서버의 무작위 티켓 콜백 주소.
- `CST_WINDOW_TYPE=submit`, `LGD_CUSTOM_SWITCHINGTYPE=SUBMIT`: 사용자 브라우저의 전체 페이지로 결제창 연결.

**실제 성공한 흐름:**

1. 사용자 브라우저가 gcloud의 티켓 링크를 연다.
2. 브라우저가 학교에서 생성된 주문·금액·서명으로 Toss 결제창을 연다.
3. 학교 쿠키가 없는 브라우저에서도 3,000원 카드 선택 화면이 정상 표시된다.
4. 사용자가 결제를 취소한다.
5. PG가 gcloud 콜백 주소로 POST하고, 시험 서버가 비성공 응답을 수신한다.
6. 사용자에게 결과 수신 화면을 표시한다. 기존 `parent.payment_return` 오류는 발생하지 않는다.

재현 서버는 `tools/certificate_payment_probe.py`에 있다. 결제 폼은 비공개 파일로 전달하고,
티켓·개인정보·PAYKEY를 요청 로그에 남기지 않는다. 콜백 결과도 결제 완료로 신뢰하지 않는다.
이 서버는 승인 요청을 보내지 않는 시험 도구이며 실제 MCP 결제 기능이 아니다.

### 실제 유료 발급에서 추가할 부분

학교의 `payment_return()`은 PG 응답 코드 `0000`과 PAYKEY를 받은 뒤
`/wm1.0/jsp/pay/lg/filepay/newcertres.jsp`에 결제 폼을 제출한다.
원격 MCP에서는 **같은 사용자의 학교 세션과 주문 상태를 서버에 유지**하고,
사용자 인증이 끝난 PAYKEY를 해당 학교 승인 경로로 전달하는 처리가 필요하다.

이후 학교의 주문·발급 보관함에서 실제 결제/발급 상태를 확인한 뒤 문서를 받는다.
브라우저가 보낸 응답 코드만 보고 발급 완료로 처리하면 안 된다.
승인 단계의 중복 요청·결과 불명 상황에서는 주문 상태부터 재조회해야 한다.
실제 유료 승인을 하지 않았으므로 PAYKEY 승인·결제 완료·최종 PDF 수신은 미검증이다.

## 유료 승인 이어받기 구현

`tools/certificate_checkout.py`에 후속 실험 서버를 추가했다. 브라우저 쿠키를 요구하지 않는
결제 링크를 제공하고, 인증 성공 응답의 PAYKEY만 원래 주문 폼에 합쳐 학교 승인 경로에 전달한다.
금액·주문번호·상점 식별자가 응답에 포함되면 원래 값과 일치하는지 검사한다.
브라우저가 넘긴 제출처·서명 등으로 서버 주문 필드를 덮어쓰지 않는다.

승인 시도 상태를 네트워크 요청 전에 디스크에 기록하며, 동일 콜백·동시 요청에 승인 요청을 한 번만 보낸다.
기존 상태 파일을 덮어쓰는 재시작도 거부한다. 타임아웃은 `approval_unknown`으로 남기고,
이후에는 승인 재요청 없이 보관함만 조회한다. PG 응답 코드나 승인 HTTP 200만으로 완료 처리하지 않는다.

보관함에서 원래 문서 번호와 같은 행의 다운로드 링크를 찾았을 때에만 파일을 요청한다.
응답이 `%PDF-`로 시작해야 PDF 링크를 제공한다. 보관함 HTML에 실제 발급 행이 없는 현재 상태에서는
이 파서의 실거래 호환성을 검증할 수 없으며, 결제 영수증 검증도 아직 구현되지 않았다.
`paid_verified`는 이 실험에서 참으로 바꾸지 않는다.

`--allow-approval`을 명시해야 실제 학교 승인 요청이 가능하다. `--consume-form`은 입력의 학교 세션 설정을
메모리에 읽은 뒤 디스크에서 삭제한다. 학교 세션은 HttpOnly `JSESSIONID` 하나만 옮겨 확인했으며,
학교 통합 SSO 토큰은 원격 결제 설정에 넣지 않았다. 학교 쿠키는 PG 폼이나 사용자 HTML에 포함하지 않는다.

### 검증

- `tools/test_certificate_checkout.py`의 13개 테스트를 로컬과 gcloud Linux x86_64/Python 3.11에서 통과했다.
- 취소, 누락 PAYKEY, 주문/금액 불일치, 중복 필드, 동시 중복 콜백, 승인 타임아웃,
  타임아웃 후 발급 조회 복구, 승인 비활성화, HTML의 PDF 오인, 재시작 중복 승인 방지를 검사했다.
- gcloud의 실제 학교 세션으로 보관함 조회에 성공했다. 브라우저만 로그인된 상태에 의존하지 않는다.
- 운영 MCP와 분리된 임시 서버에서 실제 승인 가능한 3,000원 사용자 결제 링크를 준비했다.
  공개 상태 조회 시 `ready`, `approval_attempted=false`, `pdf_ready=false`를 확인했다.
- 아직 사용자의 실제 카드/휴대폰 인증은 없으므로 실제 승인·PDF 수신 성공을 주장하지 않는다.
- 운영 MCP 코드나 서비스에는 연결하지 않았다.

## 실거래 후 발견한 문제

사용자가 3,000원 결제 승인 내역을 확인했다. 실험 서버는 학교 승인 경로를 한 번 호출했고
HTTP 응답을 받았으나, PDF 보관함과 일반 출력 보관함에 해당 재학증명서는 나타나지 않았다.
현재 상태는 `approval_returned_unverified`이며, 결제 또는 발급 완료를 코드로 확인한 것은 아니다.

초기 실험 구현은 승인 응답 본문을 저장하거나 응답의 브라우저 후속 처리를 분석하지 않고 버렸다.
따라서 승인 뒤 등록 단계가 누락됐는지 등을 해당 응답으로 확인할 수 없게 되었다.
이 부분은 구현 결함이다. 이후 코드에서 승인 응답을 0600 비공개 파일로 보존하도록 수정했고,
응답 파일 권한 검증을 포함한 13개 테스트를 다시 통과했다.

원래 승인 응답의 복구를 시도했으나 확보하지 못했다. 기존 결제에 대해 승인 재요청이나
새 결제는 실행하지 않았다. 사용자가 준 승인 내역과 원래 학교 주문을 비공개로 보존하고,
KICA에 기존 결제 건의 발급 처리 확인을 요청하는 미발송 문의 문안을 준비했다.
외부 문의 발송에는 별도 사용자 승인을 요청했다. 승인번호와 주문번호는 이 문서에 기록하지 않는다.

현재 유료 발급 경로는 실거래 완료가 검증된 기능이 아니며, 운영 MCP에 제공하면 안 된다.
기존 결제 건의 발급 등록 상태를 확인하고, 정상 승인 응답의 후속 처리까지 검증해야 한다.

## 저가 재시험 및 응답 기록 보강

사용자가 추가 결제 재시험을 요청했고, 가장 싼 방식으로 진행하도록 지정했다.
학교 화면에서 국문 재학증명서 일반 인터넷 출력 1통이 1,000원임을 확인했다.
PDF 다운로드 3,000원과 다른 상품이며, 무료 장학금 증명서 0원은 PG 승인 경로를 거치지 않는다.
기존에 승인된 3,000원 주문과 다른 주문번호인 것을 확인하고 준비했다.

일반 출력의 승인 경로는 `/wm1.0/jsp/pay/lg/smart/newcertres.jsp`다.
해당 학교 화면은 긴급연락처를 요구하므로 사용자용 결제 연결 화면에서 직접 입력받도록 했다.
연락처를 임의로 생성하지 않는다.

`School` HTTP 클라이언트는 승인 요청 전에 요청 본문을 저장하고, 모든 리디렉션의 상태·헤더·본문,
최종 응답과 HTTP 오류 본문을 비공개로 보존한다. 브라우저에서 돌아오는 콜백 원문·헤더와 해석한
콜백 필드도 보존한다. 자동 제출 폼이 있으면 원문에 남으며 현재 코드는 임의의 폼을 자동 실행하지 않는다.
승인 응답 보존 성공 여부를 상태에 기록한다.

19개 테스트를 로컬과 gcloud Linux에서 통과했다. gcloud에서 실제 학교 보관함 조회를 실행하고
요청·응답 파일 4개가 생성되며 모두 0600 권한인 것을 확인했다.
새 임시 서버는 기존 주문/서버와 분리한 포트에서 동작한다.
일반 출력 발급 내역은 PDF 수신과 구분해 `issued_native_document_ready`로 표시한다.
이 재시험도 아직 결제 성공·최종 문서 수신이 검증된 운영 기능은 아니다.

## gcloud에서 무료 증명서 PDF 자동 생성 성공

사용자가 목표를 최종 PDF 자동 수신으로 명확히 했다. 아직 승인되지 않은 1,000원 링크는 서버와
터널을 중지했다. 중지 전 `approval_attempted=false`를 확인했으며 추가 결제는 실행하지 않았다.

`tools/certificate_native_pdf.py`는 이미 발급된 장학금지급증명서를 학교 세션으로 찾아 다음을 자동 실행한다.

1. 일반 출력 보관함에서 문서 식별 및 남은 출력 매수 확인.
2. EXECHECK에서 TPID 수신, PREVIEWENC 실행 인자 수신.
3. 문서 수신, 복호화, 압축 해제.
4. 서버의 `senddocno.jsp`에서 16자리 문서확인번호 수신.
5. 원래 FastReport 페이지의 문자·그림·선을 PDF로 렌더링하고 실제 문서확인번호 반영.
6. PDF 저장 후, 실제 gcloud IP와 `rusaint PDF renderer`라는 출력 모델명으로 출력 완료를 한 번 통지.
7. `WMVERIFY?COMMAND=GETPRINTVIEWEXE` 원본확인 조회. 성공 응답과 원래 문서 번호의 일치를 검사.

gcloud Linux x86_64에서 위 전체 흐름이 성공했다. 추가 비용은 없었고, 결과는 2페이지 PDF다.
`server_verification_success=true`, `print_completion_sent=true`, `server_docno_applied=true`를 확인했다.
렌더링 결과는 문자 객체 58개, 그림 6개, 선 22개, 도형 2개이며 PDF 크기는 208,226바이트였다.
문서확인번호 기본값이 남아 있지 않고, 누락 글리프도 없음을 PDF 텍스트 추출로 확인했다.
각 원문 텍스트 줄의 PDF 포함 여부도 검사했다.

### 렌더러의 범위

`tools/certificate_render.py`는 준비된 FastReport 인쇄 페이지를 사용한다. UTF-8 선언 아래 섞인
CP949 속성을 손실 없이 정규화하고, 내장된 BMP 그림(직인·로고·검증 이미지 포함)을 사용한다.
Windows 글꼴은 공개 Nanum 글꼴로 대체하고, 로마 숫자 등의 누락 문자는 글리프별 대체 글꼴로 처리한다.
지원하지 않는 객체나 문자를 발견하면 조용히 생략하지 않고 중단한다.

원본확인번호 반영은 REPORTX의 `__SERIAL__` 객체와 4자리씩 나누는 처리 분석에 근거한다.
`senddocno.jsp` 번호를 받기만 했을 때는 원본확인이 실패했고, PDF 저장 후 출력 완료 통지까지
실행했을 때 성공한 것을 확인했다.

이 파일은 인쇄 데이터를 렌더링한 PDF로서 공급업체가 제공하는 전자서명 PDF와는 구분한다.
다른 종류의 증명서, 다른 객체 구성, 유료 결제 완료 흐름 전체를 검증한 것은 아니다.
기존 3,000원 결제 건의 발급 등록 문제도 아직 해결되지 않았다.
운영 rusaint-mcp 도구 연결은 별도 작업으로 남아 있다.

`tools/certificate_serve_pdf.py`는 완성된 한 파일만 30분짜리 무작위 주소로 전달한다.
문서·학교 쿠키·확인번호는 저장소에 기록하지 않으며, 실행 뒤 입력 세션 파일은 삭제했다.

## 결제 승인과 발급을 이어붙인 구현

유료 증명서의 결제 승인 뒤 PDF 생성까지 한 흐름으로 잇도록 도구를 정리했다.
실제 유료 승인은 이 작업에서 실행하지 않았으므로 유료 경로의 완주는 여전히 미검증이다.

공통 발급 파이프라인을 `tools/certificate_document.py`로 분리했다.
`native_previews()`는 일반 출력 보관함의 `preview()` 인자를 발급 내역으로 읽고,
`select()`는 문서 번호 또는 증명서 종류로 1건만 고르되 후보가 0건이거나 2건 이상이면 중단한다.
남은 출력 매수가 없으면 진행하지 않는다. `issue()`는 EXECHECK, PREVIEWENC, 문서 수신, 복호화,
압축 해제, 문서확인번호 수신, PDF 렌더링, 출력 완료 통지, 원본확인 조회를 수행한다.
출력 완료 통지는 남은 매수를 소비하므로 문서별 출력 디렉터리를 배타적으로 생성해 재실행을 거부한다.
`certificate_native_pdf.py`는 이 모듈을 쓰는 CLI가 되었고, 증명서 종류를 더 이상 고정하지 않는다.

`Checkout`은 `issue` 콜러블을 받는다. 일반 출력 주문의 승인 뒤 보관함에서 해당 문서를 확인하면
`issue_native()`가 발급 파이프라인을 호출하고 결과 PDF를 티켓 주소로 제공한다.
승인과 같은 방식으로 시도 상태를 네트워크 호출 전에 디스크에 기록하므로, 중복 콜백·새로고침·재시작이
출력 매수를 다시 소비하지 않는다. 실패하면 `issue_unknown`으로 남기고 자동 재시도하지 않는다.
렌더링 결과는 `%PDF-` 바이트로만 PDF로 인정하며, `issue`를 주지 않으면 기존처럼 보관함 확인에서 멈춘다.
티켓으로 공개되는 상태에는 문서 번호나 문서확인번호를 담지 않는다.

### 검증

- `tools/test_certificate_checkout.py` 25개 테스트 통과. 추가한 항목은 승인 후 PDF 생성 연결,
  중복 콜백·새로고침에서의 1회 실행, 발급 실패 시 재시도·재승인 금지, PDF 아닌 렌더 결과 거부,
  렌더러 미지정 시 기존 동작 유지, 공개 상태의 문서 번호 비노출, 보관함 파싱이다.
- `select()`의 매수 소진·후보 0건·모호한 후보·번호/종류 불일치를 실제 의존성으로 실행해 확인했다.
- 유료 결제 승인, 승인 후 보관함 등록, 유료 건의 최종 PDF 수신은 실행하지 않았다.
- 기존 3,000원 PDF 주문의 발급 등록 문제는 그대로 남아 있다. PDF(FILE) 경로는 승인 뒤
  보관함 다운로드에 의존하며, 이 연결 구현으로 해결된 것이 아니다.
- 운영 rusaint-mcp 도구 연결과 배포는 하지 않았다.

## 후속 검증 및 결제 연결 보강

- 결제 후 렌더 결과가 PDF여도 출력 완료와 학교 원본확인이 모두 참이어야 다운로드를 공개한다.
  실패하면 `issued_document_verification_pending`으로 보존하고 재승인·재출력하지 않는다.
- 보관함 문서 번호는 부분 문자열이 아닌 전체 값으로 비교한다.
- 관련 테스트 27개 통과. Rust 소스는 이 보강에서 변경하지 않았다.
- gcloud Python worker의 SSO 로그인과 유료 재학증명서 주문 준비에 성공했다. 학교가 제시한 금액은 1,000원이었다.
- `certificate_live_checkout.py`는 동일 학교 세션을 유지하며 주문 준비, 사용자 결제 인증,
  승인, 해당 문서의 PDF 생성과 원본확인, 다운로드를 연결하는 원격 실행 진입점이다.
  실행 전 복호화 파일과 글꼴, 실제 서버 IP를 검사하며 금액이 1,000원과 다르면 중단한다.
  승인 응답과 후속 통신은 비공개로 보존한다. 실제 유료 경로의 완주는 아직 확인하지 않았다.
- 승인 응답의 임의 JavaScript/자동 제출 폼은 실행하지 않는다. 후속 폼 필요 여부는
  실제 응답을 확인해야 하며, 기존 3,000원 승인 건은 재요청하지 않았다.
- 정식 MCP 도구 등록 및 운영 서비스 배포와는 별도의 임시 gcloud 실행이다.

## 유료 발급 성공 및 추가 검토 반영

사용자가 1,000원 일반 출력 재학증명서의 결제와 최종 PDF 수신 성공을 확인했다.
서버 상태도 `issued_pdf_ready`, `print_completion_sent=true`,
`server_verification_success=true`였다. 별도 PG 영수증 대조는 구현하지 않아
`paid_verified`는 여전히 false이며, 이는 발급·학교 원본확인 결과와 별개의 항목이다.
이 일반 출력 경로는 승인 후 추가 자동 제출 폼을 실행하지 않고 완료됐다.
기존 3,000원 FILE 주문의 문제 해결을 뜻하지는 않는다.

- worker의 PDF 처리를 `certificate_document.issue()`로 통합했다. CLI도 이미 같은 함수를 사용한다.
  공통 함수는 원본확인 결과를 metadata로 돌려주며, worker와 결제 서버는 미확인 PDF를 공개하지 않는다.
- worker는 PDF 진입 시 IP를 검증하며, 공통 함수도 잘못된 IP를 디렉터리 생성·네트워크 요청 전에 거부한다.
- 보관함은 `Basket.previews()`로 읽어 `preview()`와 `reportx.preview()`를 모두 처리한다.
- 무료 발급 후 최대 4회 짧게 목록을 재조회한다. 미확인·조회 오류·모호한 후보는
  `issuance_pending`으로 보존하고, 다음 prepare 호출도 발급 요청 없이 목록만 확인한다.
- live checkout의 금액 검사는 학교 주문 생성 이후다. 금액 불일치 시 승인은 보내지 않지만
  미결제 주문은 남으며 학교 안내에 따라 자동 취소된다.
- 이 수정은 결제 중인 gcloud 프로세스를 재시작하거나 교체하지 않고 로컬 소스에서 검증했다.
- 결제 테스트 27개와 worker·공통 파이프라인 회귀 테스트 10개, 총 37개가 통과했다.
  설정 오류 시 부작용 없음, reportx 보관함, 공통 발급 함수 사용과 캐시 재사용,
  원본확인 실패 시 비공개 유지, 지연 발급·타임아웃·다음 호출의 조회 전용 복구,
  모호한 발급 후보 처리를 검증한다.
- 이후 gcloud에도 같은 수정본을 버전 디렉터리로 설치하고 37개 테스트를 통과한 뒤
  증명서 스크립트 실행 경로에 반영했다. 기존 프로세스는 재시작하지 않았으므로 수정은
  다음 실행부터 적용된다. 기존 PDF 다운로드는 HTTP 200과 `%PDF-` 헤더를 확인했다.
  이는 증명서 Python 모듈의 배포이며, 정식 rusaint-mcp 도구 등록은 아직 별도 작업이다.

## 운영 구현으로 옮긴 범위 (rusaint-certi)

조사 도구(`tools/`)의 책임이 섞여 있어, 기존 rusaint 관례대로 크레이트를 새로 만들어 옮겼다.
학교 통신과 화면 파싱은 `packages/rusaint-certi`, 복호화와 렌더링은 같은 크레이트의
`report/` Python 필터, 도구 노출과 상태 보관은 `rusaint-mcp` 가 맡는다.
초기에는 파싱과 경계 조건만 단위 테스트로 확인했다. 이후 2026-11-16 gcloud 운영 MCP에서
무료 장학금 증명서와 1,000원 일반출력 재학증명서 모두 실제 신청부터 PDF 수신·학교 원본확인까지
검증했다. 신청·결제 상태와 운영 검증의 최신 내용은 [CERTIFICATE-PAYMENTS.md](CERTIFICATE-PAYMENTS.md)에 있다.

- `CertiClient`: SmartID `sToken` 으로 `/servlet/WMLOGIN` 진입 후 중간 폼 제출, 1회 재로그인,
  보관함 조회, 문서 수신·렌더·출력 완료·원본확인. 기관 코드와 문서 서버 경로는 각각 한 곳에만 있다.
- 리디렉션은 `certi.ssu.ac.kr` 의 HTTPS 기본 포트만 따라가며 인증 쿠키에 `Secure` 를 붙인다.
  요청 오류는 한 함수에서 `without_url()` 로 주소를 떼어 내므로 `sToken` 이 메시지로 새지 않는다.
- 로그아웃 링크 검사는 HTML 화면 조회에만 쓴다. `EXECHECK` 는 팝업이고 `PREVIEWENC` 는 JSON 이므로
  그 검사를 적용하면 발급이 막힌다. 실행 인자는 CP949 로 해석한다.
- 발급은 두 단계다. `render_pdf()` 까지는 출력 매수를 쓰지 않고, `complete_print()` 가 소비한다.
  호출자는 통지 전에 PDF 와 단계를 0600 파일로 남기고, 통지 뒤 오류가 나면 다시 출력하지 않고
  `verified_original()` 만 재시도한다. 원본확인을 통과하기 전에는 PDF 를 사용자에게 주지 않는다.
- 중복 출력은 작업 ID 의 1회성이 아니라 문서 번호별 기록(`StateDirectory`)으로 막는다.
  이미 출력한 문서는 다시 출력하지 않고 보관한 PDF 를 다시 전달한다.
- `tools/` 의 `certificate_probe.py`·`certificate_render.py` 사본은 조사 기록으로 남아 있다.
  운영 경로는 `packages/rusaint-certi/report/` 이므로, 실측 확인 뒤 중복을 정리해야 한다.
